# 阅读器页面图片加载失败 · 自动重试设计（v5）

> 版本基准：v1.9.2 (85) → v1.9.3 (86) → v1.9.4 (87) → v1.9.5 (88) → v1.9.6 (build 89)
> 日期：2026-10-25
> 性质：设计稿 + 四轮事故分析与实施记录。所有「现状」均经代码级核实，附文件依据。

## 一、需求

看漫画时部分页面图片加载失败，手动点「重试」即可恢复——失败多为瞬时性（网络抖动、CDN 闪断、限流），但需要用户手动介入。目标：**失败自动重试，用户无感知恢复；持久失败保留手动兜底。**

## 二、v1.9.2 方案（UI 层自动重试）与回归事故

### 2.1 原方案

新文件 `PageAutoRetry.kt`：`PageRetryState`（tick/autoAttempts）+ `PageAutoRetryEffect`（`LaunchedEffect(state, tick)`，Error 态按 1s/2s/4s 退避自动 tick++，共 3 次），驱动 model 追加 `#retryN` 强制 Coil 重新请求；用尽后回退手动「点击重试」，手动点击清零计数重新计满一轮。

### 2.2 事故

**真机阅读时卡住然后闪退**（v1.9.2 引入，v1.9.1 无此问题）。

### 2.3 事故分析（静态层面已排除的假设）

逐项核对 Coil 2.7.0 源码（compose 侧 painter 执行管线）后，以下机制均被证明有界/无死锁：

1. **painter 重启风暴**：`rememberAsyncImagePainter` 每次重组都会 `painter.request = request`（AsyncImagePainter.kt L212），但 `AsyncImagePainter.request` 是 `mutableStateOf`，且 **`ImageRequest` 实现了全字段 `equals`**（ImageRequest.kt L183）——内容相同的重建请求不会触发 `snapshotFlow { request }` 重执行；只有 data 变化（`#retryN`）才重执行。重执行次数受 attempts 计数约束（≤3）。
2. **重试死循环**：`autoAttempts` 只在 `delay` 完成后递增，effect 因 state/tick 变化重启只重置延迟不定额；手动清零仅由点击触发。数学上有界。
3. **CoalescingInterceptor 死锁**：leader 的 `finally { inFlight.remove(key) }` 保证任何退出路径（含取消）都清理窗口；等待者对已死 leader 的降级重选主逻辑自洽。
4. **CrossfadePainter 失控**：动画按 `SystemClock.uptimeMillis` 时间驱动，时长有界，无帧循环。
5. **请求无限挂起**：BcTls 未改 OkHttp 默认超时（connect/read 10s）。
6. **组合期快照写**：所有状态写（tick/attempts）都发生在协程或点击回调，无组合期写。

**结论：静态分析无法定位确定性根因**，但崩溃事实与 v1.9.2 唯一改动（UI 层自动重试机制）强相关。该机制的本质风险在于：自动重试把「一次刻意的、单次的 model 变更」变成「无人值守的、多 item 并发的、与滚动/切章/取消时序交织的重执行流」，与 painter 的 `snapshotFlow+mapLatest`（新请求自动取消在途执行）、合流器的选主/降级、交叉淡入等机制产生组合爆炸式的时序交互，其正确性无法靠静态审查穷尽验证，真机上已实际出现冻结+崩溃。

### 2.4 v2 决策：回退 UI 层机制，下沉到 HTTP 层

- **整体回退** `WebtoonSplitPage.kt` / `ReaderScreen.kt` 至 v1.9.1（8285116，经 `git diff 8285116` 验证零差异），删除 `PageAutoRetry.kt`。阅读器恢复到长期稳定的行为。
- **自动重试改在 OkHttp 应用层实现**（`image/RetryInterceptor.kt`，挂到 `BcTls.imageLoaderClient`，该 client 仅 Coil 使用）：

| 维度 | v1.9.2（UI 层） | v2（HTTP 层） |
|---|---|---|
| 重试位置 | Compose 状态驱动 painter 换 model 重执行 | 同一次 Coil 请求内部，OkHttp `proceed` 前循环 |
| 对 Coil 的可见性 | 每次重试 = 新请求（重组+painter 重启+合流重选主） | **完全不可见**（一次请求，只是更晚返回） |
| 触发面 | 仅阅读器两个渲染路径 | 所有 Coil 图片（封面等同样受益） |
| 崩溃面 | 引入回归 | **失败面严格小于 v1.9.1**（请求流同构，仅成功率更高） |
| 手动兜底 | 保留 | 保留（阅读器 UI 与 v1.9.1 完全一致） |

### 2.5 RetryInterceptor 语义

- **只重试瞬时失败**：`IOException`（连接重置/读写超时/DNS 抖动等）与 HTTP 408/429/5xx（含 Cloudflare 520-526）。403/404 等确定性失败不重试——重试无法恢复，只会拖慢出错反馈。
- **额度与退避**：最多 2 次重试（共 3 次尝试），退避 500ms/1500ms（总额外等待 ≈2s，覆盖用户「手点即成功」的瞬时窗口）。
- **取消感知**：`call.isCanceled()` 优先判断——Coil 在页面滚出屏幕/切章/退出阅读器时会取消请求，被取消的调用立即放行绝不重试；重试前关闭失败响应体，避免连接池泄漏。
- **背压**：退避用 `Thread.sleep`（OkHttp dispatcher 线程池承载，64 线程上限，失败风暴下最坏占用可控）。

## 四、第三轮（v1.9.4）：v1.9.3 仍「卡住后闪退」+ 崩溃日志丢失

### 4.1 用户反馈

v1.9.3 阅读仍会卡住然后闪退；崩溃后重新进入，应用内日志为空——LogStore 是纯内存环形缓冲，进程死亡即清零，崩溃证据无从取证。

### 4.2 根因定位（本轮已核实的事实链）

1. v1.9.3 的阅读器代码与 v1.9.1 **逐字节一致**（`git diff 8285116` 为空），代码级差异仅 RetryInterceptor（HTTP 层）。
2. 核实 Coil 2.7 `HttpUriFetcher.executeNetworkRequest`：图片请求经 `call.enqueue`（异步调度器）执行 → **受 OkHttp Dispatcher「每主机最多 5 个并发」默认约束**。
3. **重试槽位风暴**：用户网络本身频繁瞬时失败（这正是自动重试需求的来源）。v1.9.3 的每个失败请求在「退避 sleep + 最多 3 次尝试（每次最长 10s 连接 + 10s 读超时）」期间**持续占住每主机槽位**。阅读时可见页 + 预取共 5+ 个不同 URL 并发失败，5 个槽位即被重试循环占满 → 其余全部图片请求在 dispatcher 排队 → **全屏「加载中」卡死（=用户看到的「卡住」）**，持续无响应后被系统按 ANR/无响应处理或用户侧表现为「闪退」。v1.9.1 失败即单次快速返回、槽位立刻释放，无此放大效应。
4. 「闪退」的确切类别（ANR / OOM / 异常）此前无数据可证——这暴露了第二个缺陷：崩溃不落盘。

### 4.3 v1.9.4 修复（三层）

1. **RetryInterceptor 并发重试限额（治根）**：全进程 `Semaphore(3)`，进入重试前 `tryAcquire`，拿不到名额即放弃本次自动重试、按 v1.9.1 行为直接交还失败（手动重试兜底仍在）。限额 3 < 每主机 5，**数学上保证重试风暴下至少 2 个槽位留给正常请求，不可能再全局停摆**；退避缩短为 400ms/1200ms（单请求额外占用上限 ≈1.6s sleep + 尝试时间）。重试事件同步写入 LogStore（崩溃报告的证据链）。
2. **CrashReporter 崩溃落盘（治盲）**：全局 UncaughtExceptionHandler 在崩溃瞬间同步写 `filesDir/crash/last_crash.txt`（堆栈 + 应用版本 + 设备 + LogStore 尾部 + 系统 crash 缓冲尽力抓取），下次启动日志页顶部横幅呈现（查看/复制/忽略）——崩溃证据跨进程存活，后续任何闪退均可取证。
3. **MainThreadWatchdog 卡顿看门狗（补证）**：后台线程每 4s 向主线程投递心跳，3s 未到达即记录主线程调用栈到 LogStore（每次卡顿周期 ≥10s 才记一条）。「卡住」阶段若是主线程阻塞，栈会随崩溃报告一并落盘。

### 4.4 验证与发版

- `gbuild.sh assembleRelease` BUILD SUCCESSFUL；v1.9.4 (build 87)，APK/update.json 已更新并推送。
- 真机复现路径：安装后正常阅读；若再次卡住/闪退 → 重新打开 App → 设置 → 调试日志 → 顶部「检测到上次异常退出」→ 复制报告反馈。报告含确切崩溃堆栈与版本号（同时可甄别实际运行的版本）。

## 五、第四轮（v1.9.5）：v1.9.4 仍闪退且调试日志为空——闪退不是 Java 异常

### 5.1 关键推理

v1.9.4 已有 UncaughtExceptionHandler 落盘 + 启动恢复提示。用户复现闪退后调试日志**完全为空**（无横幅、无「检测到上次异常退出」日志行）⇒ 崩溃文件从未写出 ⇒ **进程死亡没有经过 Java 异常通道**。剩余可能：

1. **ANR**：主线程阻塞超时被系统终止——完美对应「卡住→闪退」表述；系统杀进程不触发任何应用层回调。
2. **系统内存不足杀进程（lmkd）**：内存压力/GC 抖动表现为卡顿，内核直接杀进程，同样无异常。
3. **手机未实际升级到 v1.9.4**（应用内更新下载失败仍运行旧版）——v1.9.4 无法自证，需版本显示。

### 5.2 v1.9.5 取证与缓解

| 项 | 内容 | 覆盖假设 |

## 六、第五轮（v1.9.6）：v1.9.5 不再闪退，但弱网下大量页面需手动重试 + 看门狗抓到 72 秒主线程冻结——mapping 反解定位**合流拦截器主线程活锁**

### 6.1 证据

用户反馈：不闪退了，但阅读时加载失败很多、需手动点重试；并提供了 v1.9.5 诊断报告——**无退出原因段**（未异常退出），但**看门狗记录 7 次、每 12 秒一次、完全相同的主线程冻结栈**（01:21:24–01:22:36，即主线程被同一调用栈连续占死 ≥72 秒）。

用 v1.9.5 构建的 mapping.txt 反解混淆栈：

| 混淆帧 | 原始 |
|---|---|
| `Q2.j.c` | `kotlin.jvm.internal.Intrinsics`（+TypeIntrinsics 合并）|
| `e2.b.a:230` | **`com.pika.image.CoalescingInterceptor.intercept`** |
| `e2.a.r:12` | `CoalescingInterceptor$intercept$1`（挂起 lambda）|
| `I2.a.l` | `BaseContinuationImpl.resumeWith` |
| `b3.I.run` ← Handler | Compose 主线程派发的 Runnable（重组）|

### 6.2 根因：首领「先唤醒后摘除」在 Main.immediate 内联恢复下活锁

完整机制（每一环都有代码/文档依据）：

1. 阅读器所有切片 painter 协程跑在 `CoroutineScope(Dispatchers.Main.immediate)`（Coil AsyncImagePainter 源码）。同一长图的多个切片经合流拦截器共享首领请求——**首领与全部等待者都在主线程上下文里**。
2. 首领失败（重试耗尽）恢复到主线程，旧代码顺序：`mine.completeExceptionally(t)` → `throw` → `finally { inFlight.remove(key) }`。
3. `Main.immediate` 的 `isDispatchNeeded()==false`（当前在主线程）→ **等待者协程在首领的 completeExceptionally 调用内部被内联恢复**。
4. 等待者 catch 异常 → while 循环 → `putIfAbsent`：**首领的摘除还没执行**（它在更深的栈帧里等这次内联恢复返回）→ 拿到的仍是已完成的旧 deferred。
5. `await()` 对已完成 deferred 走快路径**立即再抛**（不挂起、不派发）→ 再 catch → 再 putIfAbsent → **主线程无限自旋**；首领的摘除永无执行机会 → 活锁，主线程 100% CPU。
6. 触发条件随自动重试显著放大：重试延长首领存活时间 → 等待者积累更多 → 「重试耗尽失败」事件成批发生 → 弱网失败风暴 = 高频活锁。这解释了全部历史现象：v1.9.2/1.9.3「卡住后闪退」（活锁 + 触摸 → ANR 杀）、v1.9.3 回退阅读器无效（bug 不在阅读器）、v1.9.5 冻结但不再死（内存取证与并发限额生效后多数活锁可熬过/不触发 ANR）。

### 6.3 修复

**CoalescingInterceptor 首领路径改为「先摘除自己，再唤醒等待者」**：

- `inFlight.remove(key, mine)`（条件摘除，只摘自己的条目，不误删新一代首领）**前置于** `complete/completeExceptionally`；
- 摘除后等待者循环 `putIfAbsent` 必然拿到空位（成为新首领并挂起到 IO）或新在途 deferred（真实挂起），内联快路径再抛的闭环被结构性消除——即便仍在 Main.immediate 上内联恢复，也只是毫秒级换届后挂起，主线程释放；
- 代价：摘除与唤醒之间微秒级窗口内新请求可能重复发起（不合流），可忽略。

**RetryInterceptor 加强**（针对「大量需手动重试」）：重试 2→3 次（共 4 次尝试）、退避 400ms/1.2s/3s（总窗口 ≈4.6s，对齐用户手点的时间尺度）；**403 纳入重试**（CF 边缘瞬时拦截，实测手点必恢复；死链代价 ≈5s 可接受）；imageLoaderClient 每主机并发 5→8（浏览器同源量级），并发重试限额 3→6（恒保持 ≥2 槽位给正常请求，v1.9.3 卡死教训的约束不变）；重试耗尽记录失败原因进应用日志。

### 6.4 发版与验证

v1.9.6 (build 89)，BUILD SUCCESSFUL。预期：主线程冻结消失（活锁根除）；弱网失败页面绝大多数自动恢复（4.6s 窗口 + 403 重试 + 更高并发）；残余失败在应用日志中留有原因（RetryInterceptor W 级日志），可按数据继续调参。

## 七、第六轮（v1.9.7）：v1.9.6 后偶发失败仍需手点 + 失败证据随进程死亡丢失

### 7.1 现象与证据缺口

用户反馈（v1.9.6）：看漫画仍有「有的页」失败需手动点（较 v1.9.5 的「很多」明显减少）。贴出的日志仅有启动行与详情页行，**没有任何 RetryInterceptor 记录**——不是没有失败，而是 LogStore 内存态随进程死亡清零：用户复现失败的进程结束后再打开查日志，永远只能看到新会话。同时日志提示存在待查看的诊断报告（上次会话证据已落盘），但报告内容未反馈。

### 7.2 措施

1. **失败取证持久化（治盲区）**：RetryInterceptor 的「重试耗尽」与「并发限额受限」两类事件除写 LogStore 外**追加落盘** image_failures.log（64KB 上限）；下次启动并入诊断报告呈现，「忽略」时一并清除。此后任何一次「失败→手点」复现，重启后即可拿到确切失败原因（HTTP 码/异常类/URL），按数据调参而非猜测。
2. **重试窗口拉长（治症状）**：重试 3→4 次（共 5 次尝试），退避 400ms/1.2s/3s/6s + 0-400ms 抖动（防弱网恢复瞬间多页同步重试形成风暴），总额外等待 ≈10.6s——继续向「用户注意到失败并手点」的真实时间尺度靠拢。
3. 并发限额 6、每主机 8 维持不变（结构上已证明不会饥饿/活锁）。

### 8.2 取证过程

1. 用户操作时段（v1.9.7 调试版）：页面几乎全部失败需手点，但 RetryInterceptor **零记录**、image_failures.log 空——失败不在 HTTP 头层。
2. 自行冷缓存读整章（健康网络）：仅 1 次头层瞬时失败被自动重试救回——故障是**时段性**的（代理节点突发不稳）。
3. 加装 ErrorLoggingInterceptor（Coil 管线末端记录最终失败原因）后故障期已过，无法自然复现 → **主动注入故障**：自写截断代理（tools/trunc_proxy.py，把每条图片响应在 64KB 处掐断，仅影响前 60 条隧道，之后恢复——精确模拟「体流中断 + 数秒后自愈」的真实形态）。

### 8.3 根因确证

截断代理下捕获：`CoilRetry: 图片管线失败(EOFException: null)`——**响应体流中途断裂**。此类失败发生在 OkHttp 拦截器返回**之后**（拦截器只见响应头），任何 HTTP 层重试机制对它完全不可见；而页面失败率与代理链路稳定性强相关，手动点击（数秒后的全新完整请求）恰逢故障间歇恢复故必然成功。这解释了全部现象：头层零记录、失败文件空、手点必好。

### 8.4 修复：CoilRetryInterceptor（管线级重试）

- 位置：Coil components 最外层（错误取证之下、合流之上），对**最终失败结果**重试。
- 范围：仅重试 `IOException` 形态（体流/解码）——头层失败（HttpException）已由 RetryInterceptor 用尽预算，不叠加（避免最坏 5×N 次尝试）。
- 策略：第 1 次重试用原请求（500ms 后）；第 2 次禁用磁盘缓存读、强制完整新下载（2s 后，绕过可能被半截响应污染的缓存条目，成功仍写回）。
- 约束：全进程并发重试限额 4（信号量 tryAcquire，拿不到名额按无此拦截器交还）；取消立即放行（proceed/delay 抛 CancellationException 天然终止）；重试与耗尽均记 logcat + LogStore + 落盘。
- **截断代理实测**：连续 60 条隧道被掐的极限注入下，6 次失败中 5 次被自动救回（含一次第 2 次重试成功）；真实间歇性故障的恢复率预期接近全量。

## 九、第八轮（v1.9.9）：用户关键证词「性能优化之前的版本没问题」——v1.9.0 的"正常"是冗余碰运气

### 9.1 证词解读

用户明确指出 v1.9.0（性能优化前）没有失败问题。v1.9.1 中图片路径的唯一行为差异是 CoalescingInterceptor（合流）：此前一张长图的最多 6 个切片各自独立并发下载——网络阵发抖动只挂掉其中一路，其余成功进缓存，页面"看起来正常"（**冗余掩盖了网络问题**）；合流后一张图只有一次下载机会，单次体流中断即整页失败。合流本身无 bug，它去掉的是"买六次彩票"的运气，把一直存在的网络阵发断流暴露成了用户可见的失败。v1.9.0 时代的 API 连接复用改动（PicaHttpEngine）不涉图片路径，排除。

附带排除：模拟器空闲 10 分钟后翻页零失败——代理不会因空闲杀连接，触发器就是阵发不稳本身。

### 9.2 加固（v1.9.8 → v1.9.9）

CoilRetryInterceptor：重试 2→3 次（500ms/1.5s/3s，总窗口 ≈5s，覆盖阵发时长）；并发限额 4→8（管线重试退避为协程 delay，不占网络通道/线程——与 v1.9.3 的 Thread.sleep-占槽事故机理不同，提高限额无卡死风险）；第 2 次重试起绕过磁盘缓存读。

## 十、残余风险与教训沉淀

- ApplicationExitInfo 需 API 30+；Android 8-10 靠心跳只能判定「前台异常终止」。
- 重试窗口再拉长的边际收益递减（超过用户手点间隔后无意义），10.6s 已接近上限；再往下应靠数据分流而非继续加码。
- 教训沉淀：① 对「自动、并发、与生命周期时序交织」的请求重执行，优先选择对上层完全透明的层实现；② **任何重试机制必须先回答「重试期间占用了什么资源、上限是多少」**；③ **「闪退」≠「Java 异常」——取证必须覆盖 ANR 与系统杀进程通道**；④ **共享协程原语（deferred/await）与「immediate」派发器组合时，完成回调的执行顺序（先清理后唤醒）是生死线**——生产者唤醒消费者前必须先释放公共资源；⑤ 混淆栈不可怕，mapping.txt + 构建产物让每次真机事故都可精确归因；⑥ **取证链必须与被取证的进程同寿命——内存态日志对「跨进程死亡」类问题毫无价值**。
