# 2026-09-04

## Pika 列表页更新时间研究 · 探测脚本实测（同项目延续）

背景：昨天（09-03）完成的可行性研究留下两个未验证项：① 分类浏览接口到底返不返回 `updated_at`；② 随机/推荐接口。今天尝试跑脚本实测。

### 实测结果（重要，可复用）
- **Node 的 fetch 不会被哔咔的 Cloudflare Bot Management 拦**。挂代理后 6 个接口全部返回标准 `HTTP 401 / code=401 unauthorized`，说明签名 + 请求头 + 域名轮换全部正确，服务端正常响应。
  - **判读口径**：被 Bot Management 拦 = `403` 或业务 `code=1023`；`401 unauthorized` = 通道正常、仅缺鉴权。之前担心的"Node 被拦"并没有发生。
- **哔咔所有列表接口都必须鉴权，免登录一律 401，没有任何可绕开的公开列表接口**：`categories`、`comics?c=`、`comics/leaderboard`、`comics/random`、`comics/advanced-search`、`users/favourite` 全部 401。
  - → `tools/pica-api-check.mjs` 想跑出结论，**必须提供能登录的哔咔账号**（`PICA_EMAIL`+`PICA_PASSWORD` 或 `PICA_TOKEN`）。
- 用户本轮选择"先不测"，未索取凭据。

### 运行方式（已验证可用）
```
NODE_USE_ENV_PROXY=1 HTTPS_PROXY=http://127.0.0.1:7897 \
PICA_EMAIL=xxx PICA_PASSWORD=yyy node tools/pica-api-check.mjs
```
Node 会有 `[UNDICI-EHPA] Warning: EnvHttpProxyAgent is experimental` 警告，无害。

### 坑
- **Bash heredoc 写 .mjs 会被 shell 做变量替换**（`${n.padEnd(18)}` 报 `Bad substitution`），即使 `<<'EOF'` 加引号也失败。→ 写脚本一律用 Write 工具落文件，不要用 heredoc。
- 全盘 `grep -r ~` 搜凭据极慢（跑 4 分钟未完成），别用。

### 零凭据替代方案（已写进报告给用户）
真机上打开**搜索页 / 收藏页 / 排行榜**，看卡片封面下方有没有灰色小字日期（如 `2026-05-06`）。有 → 接口确实返回 `updated_at`；无 → 数据为空。

`pika-updatedat-feasibility.html` 第六节补入上述两条实测结论 + 401 接口清单 + 零凭据替代方案；第七节"下一步"改为以真机目视确认为首选。临时脚本 `tools/_pica_probe_tmp.mjs` 已删除。

## 关注流"刷新后内容不一致"根因排查（同日第二轮，仅分析未改代码）

用户反馈：首页「关注」Tab 经常刷新后内容显示不一致。逐行读完 `ui/home/HomeViewModel.kt` + `data/{FollowSettings,AuthorFavourites,FollowFeedCache}.kt` 后定位到 5 个原因，按严重度排序。

### P0（头号原因）：无节流串行请求 → 触发哔咔全局 60 秒限流 → 后续关注来源被静默丢弃
- `fetchTargetPage()`（HomeViewModel.kt:249-276）用**普通 for 循环串行**遍历 `targets`，**来源之间没有任何 delay**，且单词/作者分支**不走 `searchWithRetry`**（无重试）。只有多词分支才有 `Semaphore(4) + delay(250)`。
- `PicaClient.safeCall()`（PicaClient.kt:52-97）：命中 429/1023 → `attempt==0` 时切域名重试一次；**再失败则设置 `rateLimitedUntil = now + 60_000`** —— 这是 **全局** 冷却。
- 冷却生效后，**后续所有** `safeCall` 在进入时就 `throw PicaException("请求过于频繁(429)")`。
- `fetchTargetPage` 里每个 target 单独 `catch (e: Exception) { targetEnded[key]=true; emptyList() }` → **失败被完全静默吞掉**，用户无任何提示。
- 净效果：关注来源 > 2~3 个时，一次刷新只有前几个来源有数据；60 秒冷却过后再刷新又全恢复。→ 完美解释"经常且看起来随机"。

### P1：多词关注的"拉全量分页"存在分页漂移 + 120 秒超时
- `fetchKeywordPage()`（:284-338）先拉每个词第 1 页取 `pages`，再并发拉 `1..pages`（上限 50 页 × 20 条/页 = 1000 条/词）。
- 拉取过程持续几十秒，期间有新作品上传 → 按 `s=dd` 排序时整体后移 → **各页在不同时刻拉取、漂移量不同 → 重复 + 丢条目**，每次刷新的结果集都不同。
- 交集只从 `wordSets[0]` 取 id 匹配其它词（`common = wordIds[0].filter{...}`），第一个词被 50 页截断的部分即使其它词有也进不来。
- `withTimeout(120_000)` 超时会抛异常 → 同样被 catch 静默吞掉 → 该来源本次整体消失。

### P2：错误/空状态具有误导性
- 若**所有**来源都失败 → `mergeIntoFeed` 里 `merged.isEmpty() && !append` → `_followEmptyHint = "关注的内容暂无更新"`，而 `_followError` 仍为 null → **用户看到"暂无更新"，实际是全量请求失败**。
- `refresh()` 的 `catch (e: Exception)` 会捕获 `CancellationException`（它继承自 `IllegalStateException`）。快速连续下拉刷新两次 → 第一次被 cancel → 旧 job 的 catch 可能在新 job 清空 error **之后**执行 → 残留"刷新失败"横幅，但数据其实是新的。

### P3（潜在）：`createdAt` 缺失导致关注来源顺序每次读取都可能变化
- `AuthorEntry.createdAt`/`FollowItem.createdAt` 声明为 `= System.currentTimeMillis()`（默认值而非可空）。
- `AuthorFavourites.get()` / `FollowSettings.items()` 都用 `.sortedByDescending { it.createdAt }`。
- **v1.5.0 之前存的旧条目 JSON 里没有 `createdAt` 字段** → 每次反序列化都重新生成新时间戳 → **排序结果每次读取都不一样** → `rebuildTargets()`（每次 refresh 都调）产出的 `targets` 顺序随机。
- 影响：① 加剧 P0（每次是**不同的**来源被限流牺牲掉，所以看起来随机）；② `distinctBy { it.id }` 保留项变化；③ 并列排序的 tie-break 变化。
- 注：只要用户在 v1.5.0 之后新增/删除过任一关注项，`add()/remove()` 会整体重新序列化，旧条目会被"治愈"。所以是条件性问题。

### P4：`take(120)` 截断边界
- 排序后硬截断到 120 条（`_followEndReached` 恒为 true，不滚动加载）。任何来源的内容变化都会让边界附近的条目进出，属固有抖动，可接受。

### 待确认
需用户提供：关注了多少个作者 / 多少个关键词（其中几个是多词）。若 > 3 个来源，P0 基本可确认。

### 用户补充（坐实 P0）
"我只有作者关注，没有关键词关注，作者关注了 5 个" → **5 个作者串行零间隔请求，第 3 个来源起必撞限流**，P0 确认；**P1（多词分页漂移）对当前配置不适用，暂缓**。

### 已实施的修复（P0 + P2 + P3，编译 + 打包通过）
四个文件：

1. `ui/home/HomeViewModel.kt`
   - 新增 `TARGET_REQUEST_INTERVAL_MS = 600L` 与私有数据类 `FollowFetchResult(items, failedCount, rateLimitSeconds)`；新增 `import kotlinx.coroutines.isActive`。
   - `fetchTargetPage()` 返回类型改 `FollowFetchResult`：循环开头先查 `PicaClient.rateLimitRemaining() > 0` → **直接 break 停止本轮**（此前会继续请求、不断续期 60s 冷却）；来源之间 `delay(600)` 节流；作者分支从裸 `source.search()` 改走 `searchWithRetry`（此前作者/单词来源零重试，一次抖动整源消失）；统计 `failed + (pending.size - started)` 把"因限流从未开始的来源"也计入失败数。
   - `refresh()`：全部失败时**跳过合并保留上次内容**（避免空结果清空列表并误报"暂无更新"）；部分失败时 `mergeIntoFeed(..., append = true)` **只增不减**；仅 `totalFailed == 0` 才 `_refreshTick++` 回顶；按「限流且全空 / 限流但部分成功 / 全失败 / 部分失败」四种情况给分级文案；`catch` 中 `if (e is CancellationException) throw e` 放行取消；`finally` 用 `if (isActive)` 守卫，避免旧 job 关掉新刷新的转圈。
   - `fetchKeywordPage()` 单词分支同样改走 `searchWithRetry`。
2. `data/AuthorFavourites.kt`：`AuthorEntry.createdAt` 改 `Long? = null`，`get()` 改 `.sortedByDescending { it.createdAt ?: 0L }`，`add()` 显式写 `createdAt = System.currentTimeMillis()`。
3. `data/FollowSettings.kt`：`FollowItem.createdAt` 同样改可空 + 同上排序。

**核心教训（可复用）**：kotlinx.serialization 里**千万别给持久化字段写 `= System.currentTimeMillis()` 当默认值** —— 旧 JSON 缺失该字段时每次反序列化都生成新时间戳，排序结果每次读都不一样，是极隐蔽的"随机性"来源。要写 `Long? = null` 并在排序处兜底。

### 追加修复（同日第三轮，用户说"继续"后自查发现的两处）
1. `searchWithRetry()` 重试循环补 `if (e is CancellationException) throw e` —— 原先靠 `delay` 在已取消作用域里抛 CancellationException 的副作用才没出事，属于隐性正确；显式放行保证新刷新接管时旧重试立刻停。
2. `refreshOnResume()` 的排行榜 TTL 刷新与关注刷新**同时开跑**：排行榜 1 个请求和关注流第 1 个请求几乎同瞬间发出，叠加顶到哔咔 2 次/秒限流线；排行榜先撞限流会设 60 秒全局冷却直接拖垮关注流。→ `loadRank()` 加 `startDelayMs: Long = 0` 参数，`refreshOnResume` 传 2000ms 错峰（切榜/下拉刷新等其它调用点用默认 0，行为不变）。
- 复盘：这类"多路刷新并发打同一限流 API"的场景要整体看请求时间线，只修单条路径仍会漏。若后续还有零星限流，下一步方案是给 `PicaClient.safeCall` 加全局令牌桶/最小间隔（未做，涉及网络层改动较谨慎）。
