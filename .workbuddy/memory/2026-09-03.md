## 禁漫源（JMComic）功能规划方案（未写代码，仅设计）

产出：`jm-source-plan.html`（项目根目录，52KB，单文件，含可交互 UI 原型）。

### 调研结论（基于现有代码 + 社区 SDK 文档）

**现状（逐行复核后的精确数字）**：`Source` 接口 **27 个方法**——9 个抽象方法（`login/logout/categories/browse/search/hotWords/comicDetail/chapters/chapterPages`）禁漫**全部实现**，另 override 了 `supportedSorts` 属性（限定 LD/VD 两种）；剩余 **18 个走默认实现，其中 17 个直接抛 `UnsupportedOperationException`**，仅 `tags()` 返回空列表。即：必须做的都做了，17 项可选能力全部不可用。`JmClient` 实际只有 6 个端点。

**最紧迫问题不是功能少而是会崩**：UI 层只有详情页（收藏、评论）对 `UnsupportedOperationException` 做了 try-catch。收藏页、首页排行榜、首页随机推荐、"我的"页 profile、"我的评论"页都是直接调用无降级。→ 建议先引入 `SourceCapability` 能力声明机制做全局止血。

**禁漫移动端 API 端点**（现有代码实测前缀 `/api/v3/*`）：
- 已接入：auth/sign-in、categories、commend_list_page、search、album/{id}、album_page/{aid}/{photo}/{page}
- 规划接入（社区 SDK 源码整理，**前缀需抓包核对，不要照抄**）：
  - `/categories/filter` page·c(分类)·o(mr 最新/mv 观看/mp 图片/tf 喜欢/mv_t 日榜/mv_w 周榜/mv_m 月榜)·t(t 今日/w 周/m 月/a 全部) → browse + rank
  - `/favorite` GET(收藏列表, 每页约 20) / POST {aid}(切换收藏)；**移动端不支持 folder_id 参数**（社区 SDK 明确注释）→ 只用默认收藏夹，UI 与哔咔一致
  - `/chapter_view_template?id={photo_id}&mode=vertical&page=0` → 响应 HTML 里正则取 `var scramble_id = (\d+);` 用于图片解码
  - `/setting` → 域名/图片 host 列表，可做自动分流替代设置页手填
  - `/search?main_tag=n` → 0 综合/1 作品/2 作者/3 标签/4 角色
  - 评论、用户资料/签到/历史：端点待抓包确认

**禁漫侧关键常量**：分类固定枚举 10 个（0 全部/doujin 同人/single 单本/short 短篇/another 其他/hanman 韩漫/meiman 美漫/doujin_cosplay/3D/english_site/禁漫漢化組），无封面图。

### 六大差异
1. **图片 scramble 解码（最大差异，P0 风险）**：禁漫图片分段打乱存储，需按 scramble_id（220980 不分割 / 268850 / 421926 新算法）还原。当前 JmClient 直接拼 `https://{host}/media/{folder}/{name}` 给 Coil，**无解码环节**（全项目 grep 无 scramble 相关代码）。→ 需先抽样 10 本不同年代本子验证是否真需要解码，再决定工作量（0.5 天 vs 2 天 vs 不用做）。下载模块必须存还原后的图。
2. 排序：禁漫当前是"取回一页后客户端重排"→ 翻页后乱序（隐性 bug）。改接 `/categories/filter` 交服务端。ComicSort 映射：DD→mr、LD→tf、VD→mv、DA→mr+客户端反转（禁漫无升序参数）。
3. 收藏：移动端无 folder_id，语义与哔咔一致，UI 不动。
4. 分类：固定枚举无封面 → 分类页需从封面网格切为 chip 墙；分类管理（排序/隐藏）对禁漫隐藏。
5. 搜索：main_tag 维度切换，比哔咔"统一搜"更贴合禁漫习惯；汉化组/上传者/完结状态筛选对禁漫隐藏。
6. 账号：禁漫无等级/经验/称号（ComicUser level/exp 留 0，UI 隐藏）；禁漫独有每日签到 + 浏览历史。

### 建议路线
- P0（2~3 天）：能力声明机制止血 + 图片解码验证与实现 + categories/filter 排序 + /favorite 收藏 + 排行榜 + 搜索维度 + 分类页适配
- P1（2~3 天）：评论、个人资料、随机/相关推荐兜底、热词标签、域名自动分流
- P2：签到、浏览历史、账号管理、小说/画册（建议单独立项）
- **第一步建议**：花半天做两件事——抓包确认端点路径前缀 + 抽样验证图片是否需要解码。这两件事决定 P0 真实工作量，在此之前不动业务代码。

## 追加：禁漫接口实机验证（同日第三轮）— 推翻多个前两轮假设

产出：`jm-api-verification.html`（项目根目录，32KB，7 节）。用 Node 脚本发真实请求，实现签名与解密后逐端点验证。

### 🔴 推翻的假设
1. **`/api/v3/` 前缀已废弃**。实测任何 `/api/v3/*` 路径都返回 `{"code":200,"errorMsg":"Not legal.api"}`。**正确路径无前缀**：`/categories`、`/categories/filter`、`/search`、`/album?id=`、`/chapter?id=`、`/login`、`/forum`、`/favorite`、`/setting`、`/week`、`/daily_chk`、`/watch_list`、`/chapter_view_template`。
2. **图片不需要解码**（前两轮判断为最大 P0 风险，实测不存在）。跨 2018~2026 年 **20 个本子**全部 `scramble_id=220980`（不分割）；10 本子实下载首图/中图全部 HTTP 200 合法 WEBP（960×1342 ~ 1280×1790）。→ **直链 + Coil 即可，无需写解码算法**（建议保留 scramble_id 探测做防御）。
3. **`t=` 时间筛选参数无效**。`/categories/filter` 上 a/t/w/m 返回内容完全一致 → 方案里的「时间范围筛选」亮点功能应删除。
4. **`c=3D` 映射错误**（返回"其他類"）、**`c=meiman` 映射错误**（返回 English Manga）。→ 分类值必须从 `/categories` 的 `slug` 动态取，不能硬编码。

### ✅ 实测可用的正确机制（前两轮完全缺失）
- **API 域名**（原 `api.jmcomic1.com` 已失效）：`www.cdngwc.cc` / `www.cdnhjk.net` / `www.cdngwc.net` / `www.cdngwc.club`
- **签名**（缺了就是 401 `Not legal request`）：header `token=md5(ts+"185Hcomic3PAPP7R")`、`tokenparam="{ts},2.1.5"`，ver 取 `/setting` 的 `jm3_version`
- **响应解密**（data 默认是密文）：base64 → **AES-256-ECB**（注意是 256，md5 hex 32 字符）key=`md5(ts+secret)` → 去 PKCS7 padding。⚠️ `/setting` 的 data 是**明文对象**，需对 `JsonPrimitive.isString` 判断后分支处理。
- **图片 URL**：`https://cdn-msp.{domain}/media/photos/{photoId}/{filename}`（CDN：cdn-msp.jmapiproxy1.cc 等 6 个）
- **封面 URL**：`/media/albums/{albumId}.jpg`（46KB），高清 `/media/albums/{id}_3x4.jpg`（67KB）；**`.webp` 后缀返回 502**。列表接口 `image` 字段恒为空。
- **分页**：每页 **80** 条（非 20）；page 1~1000 均有数据无深度上限；`total` 恒 10000 是服务端硬上限，**不可信**。
- **scramble_id 提取**：`/chapter_view_template` 返回 HTML（不是 JSON，正常），正则 `var scramble_id = (\d+);`；该端点用**另一个密钥** `18comicAPPContent`。

### 功能可用性结论
- **免登录可用 12 项**：categories(/categories，含 slug+子分类)、browse+rank(/categories/filter，o=mr/mv/mp/tf/mv_t/mv_w/mv_m 全部生效，日榜109/周榜501/月榜442)、search(/search，main_tag 0site/1work/2author/3tag 生效)、comicDetail(/album?id=，含 related_list 约20条可做相关推荐)、chapterPages(/chapter?id=，一次返回整章 images 列表)、图片、封面、comments(/forum?mode=all&aid=)、/week 每周必看、login(POST form，参数名是 username/password 不是 email)
- **需登录 4 项**：/favorite GET+POST（401 auth_fail，端点真实存在）、/daily+/daily_chk、/watch_list（401 Authentication fail，端点存在；`/history` 才是 Not legal）
- **不可用 5 项**：hotWords（无端点，/hot_search 等全 Not legal）、tags（无端点，需从 /album 的 tags[] 聚合）、randomComics（无端点，需随机页码+本地抽样兜底）、profile（/user_profile Not legal，资料只能从 /login 响应取）、sendComment（移动端不支持，需网页端）

### 关键矛盾点（下次接手先看这条）
- `HomeViewModel.kt:259` 注释（来自 v1.5.7 提交 `366ef77`）："浏览接口不带时间字段，搜索接口按更新时间返回"。
- 但 `Doc`（PicaModels.kt:104）恰恰是**浏览接口的解析模型**，且声明了 `@SerialName("updated_at")`。两者不能同时成立 → **必须实测**。

### 证据链方法（可复用）
- 两个 Go 库（gopica / pica-go）列表结构体**都缺** `updated_at`，但它们**同时缺 totalViews/totalLikes/tags**（本项目确定在用）→ 只是作者懒得声明，**不能作为"服务端不返回"的证据**。
- **决定性正面证据**：`zhenghengbing/pica-cli` 的 `src/types.ts` —— `Comic` 类型含 `updated_at`/`created_at`，且 `PageSearch = Page<Comic>`、`PageFavorites = Page<Comic>`、`leaderboard()` 返回 `Comic[]`。→ 搜索/收藏/排行榜三项**确实返回** updated_at。

### 顺带发现的排序隐患
`BrowseViewModel`/`AuthorViewModel` 对哔咔按 `updatedAt` 字符串本地重排（DD 降序 / DA 升序）。若浏览接口时间**全空**，`sortedBy` 稳定排序 → 保持服务端顺序，暂不出错但本地重排空转；若**部分有部分无** → 顺序错乱成 bug。所以澄清该字段不只是显示问题。

### 唯一真正的 UI 缺口
详情页「猜你喜欢」`RecommendCard`（ComicDetailScreen.kt:537-565，96dp 横向卡）**只有封面+标题，没有时间行** → 即便补上数据也显示不出来。

### 处置建议
- 方案 A 零改动（若实测数据已到位）；方案 B 补 `RecommendComic.updated_at`（1-2 行）；方案 C 对列表逐条调详情接口补时间 → **不推荐**（每页 40 条 = 40 次请求，哔咔限速 ~2/s 必触发 429/1023）。
