# PiKA 工程事故复盘与经验教训

> 目的：记录这个项目是如何从「能跑」滑向「越修越脆」的，以及哪些验证环节曾经失效。
> 面向未来的 agent / 维护者：不要重复同样的路径，不要用同样的方式证明「没问题」。
> 配套硬规则见根目录 [`AGENTS.md`](../AGENTS.md)。

## 0. 一句话结论

**大多数严重问题不是「不会写代码」，而是「用错误的证据证明它对」。**
构建成功、静态审查、happy path 手点、提交说明里的「零崩溃」，都曾经被当成可运行证据，
而真正的问题藏在初始化顺序、协程取消、响应体流中断、服务端契约和分页边界里。

## 1. 代表性事故时间线

| 版本/时间 | 表面症状 | 真正根因 | 当时的验证漏洞 |
|---|---|---|---|
| v1.5.x 收藏 | 收藏按钮状态反复错 | 服务端返回 `{"action":"favourite"}` / `"un_favourite"` 机器码，代码三次猜中文文案 | 没有抓真实响应；只改字面量，没有契约测试 |
| v1.7.0 冷启动 | 每次启动必崩 `ExceptionInInitializerError` | `DownloadPrefs` 的 Flow 写成属性初始化器，首次引用 object 时 `<clinit>` 解引用尚未 `init` 的 `lateinit appContext` | 只跑了 `assembleRelease`；静态审查把「Flow 懒」误判为初始化也懒；没有冷启动冒烟 |
| v1.9.2 | 阅读器卡顿 + 闪退回归 | 自动重试放在 UI 层（painter/model 重启），触发重组风暴 | 用「功能可用」代替「性能/生命周期验证」 |
| v1.9.3→1.9.4 | 重试并发限额导致全屏卡死 | 重试信号量 3 < 每主机并发 5，重试占满槽位，正常请求饿死 | 只在理想网络下测；没有并发/弱网压测 |
| v1.9.7 | 弱网页面大量失败，手点必好 | 失败发生在响应体流中断/解码阶段，HTTP 层重试看不见 | 只测 HTTP 状态码，不测流中断；没有截断代理注入 |
| v1.9.10 | 重试后成功仍被记为失败 | 用 `attempt >= MAX` 判定「用尽」，没看最终响应是否 2xx | 没有对「失败统计」做断言 |
| v1.9.11 | 首领失败连坐全部切片 | `ErrorResult` 被共享给等待者，失去多路冗余 | 只测成功合流，不测失败合流 |
| v1.9.12 | 合流等待者全部失败且绕过日志 | 直接转交首领 `result`，Coil 校验 `result.request.target` 抛 ISE | 单测/联调只覆盖「首领成功」路径 |
| v1.9.13 | 一次发版塞 22 项修复 | 长期欠账集中偿还，回归面巨大 | 没有小步提交/小步验证 |
| v1.12.x | 选中态统一后仍出现深色描边/对比度回归 | 组件收敛了，但颜色语义仍在各页面手写 | 只验证「选中/未选中」存在，没有量化对比度与深色实测 |
| 2026-11 | 代码可维护性下降 | 自动化补丁复制粘贴、全限定名、魔法数字、死代码、无测试 | 没有代码质量门禁，只以「能编译 + 手点通过」收尾 |

## 2. 根因拆解

### 2.1 症状驱动打补丁，而不是在正确层次修复

图片加载链路最终叠了三层：

1. `RetryInterceptor`（OkHttp，HTTP 头层）；
2. `CoilRetryInterceptor`（Coil 管线，响应体/解码层）；
3. `CoalescingInterceptor`（同 URL 合流 + 失败重选首领）。

每一层单独看都有充分理由，但它们是**连续几次事故后逐层加上的**。结果是：
- 同一请求可能经历多次重试，最坏尝试次数相乘；
- 失败语义分散在三个类里，排查时必须同时读三份注释；
- 任何一层调整并发/顺序，都可能让另外两层的前提失效。

**教训**：先画清楚失败发生在哪一层（连接？响应头？响应体？解码？），再决定修哪一层。
如果必须叠层，先把每层契约写成测试，并在一个总览文档里画顺序。

### 2.2 用「猜」代替「观测服务端契约」

收藏接口的 `action` 字段被三次改错：`contains("藏")` → 恒假、`contains("收藏")` → 又恒假。
真正可靠的做法是：从设备里取 token，按 App 相同签名直打接口，记录真实响应（项目里已有
`tools/pica-api-check.mjs` 这个范本）。**一次真实抓包胜过十次语义猜测。**

同类问题：作者搜索到底走 `a` 参数还是关键词搜索、标签参数是 `categories` 还是 `tags`、
分页 `pages` 是总数还是总页数——都必须以实测响应为准。

### 2.3 把「构建成功」当成「可运行」

v1.7.0 的冷启动崩溃在编译期完全合法。`lateinit` + object `<clinit>` + 属性初始化器
是静态审查最容易漏的组合，因为代码「看起来」是懒的。
只有冷启动一次才能暴露。

**教训**：启动路径（Application、MainActivity、全局单例 init、DataStore 预热、Coil 装配）
是最高风险区。任何触碰这些地方的改动，验证门槛必须是「全新安装冷启动 + 覆盖安装冷启动」。

### 2.4 用 happy path 代替故障注入

v1.9.x 的一系列问题都只在弱网/截断/限流下出现：
- 响应体流中断（`EOFException`）在 HTTP 层不可见；
- 重试并发占满槽位会让正常请求饿死；
- 首领失败会被合流共享；
- 分页空页会让游标不前进。

这些都不是「点两下正常页面」能发现的。项目后来引入了截断代理、限流模拟、失败注入，
问题才被逐个定位。

**教训**：网络相关改动至少覆盖：断网、超时、403/429/5xx、响应体截断、并发 5+ 路、
取消（滚出屏幕/切章）。没有故障注入，就不要说「弱网没问题」。

### 2.5 没有回归测试，只有一次性手测

在 2026-11 清理前，21k 行 Kotlin 只有 5 个测试文件，覆盖 `ComicRef`、`AuthorName`、
下载清单兼容、最近阅读 ref、Webtoon 行换算。真正复杂的逻辑——
多词搜索游标、分页切片、页码窗口、失败重试、合流、下载调度——几乎没有测试。

后果是每次改动都靠「我记得上次手测过」，而手测不会覆盖边界：
空页、第 0 页、最后一页、取消、限流、重复 id、旧数据缺字段。

**教训**：纯函数优先（筛选/排序/分页/窗口/解析/状态机），先写测试再改。
测试不是覆盖率数字，而是「这个 bug 再出现时会不会红」。

### 2.6 自动化补丁的「局部正确」累积成全局屎山

典型痕迹：
- 338 处 `com.pika.xxx.Yyy` 全限定名（改一处时为了省 import，直接写全路径）；
- 同一段筛选/排序在 `BrowseViewModel` 和 `AuthorViewModel` 各一份；
- `20` / `19` 分页魔法数字散落在两个 Screen 和 ViewModel；
- 解码宽高上限在 `ReaderViewModel` 和 `WebtoonSplitPage` 各一份（注释还写着「必须一致」）；
- 网络计费判定在两个文件各一份；
- 网格间距在真实网格与骨架屏各一份；
- 死代码 `Purple80` 等兼容别名保留了很久。

这些单点都不致命，但叠加后：
- 改一个排序要改 4 个地方；
- 改一个页大小要全局搜索 20；
- 新人不知道哪份是准的；
- review 时间被噪声吃掉。

**教训**：同一语义只允许一个实现。第二份出现时立即提取；提取不了就写注释说明为什么。
机械改动后必须做一次「去重/收敛」而不是继续堆。

### 2.7 注释与代码漂移

`CategoryScreen` 曾注释「支持排序 + 连载状态筛选」，但界面根本没渲染状态筛选；
`ReaderViewModel` 注释「与 WebtoonSplitPage 保持一致」，实际宽度写死 2160，
而共享常量是另一个值。注释越详细，漂移时误导性越强。

**教训**：注释只写「为什么」和「约束」，不要复述 UI/字段清单；
改代码时把相关注释当成代码一起改；能用类型/常量表达的，不要用注释表达。

### 2.8 发版流程靠人肉记忆

版本号、`update.json`、sha256、APK 复制、提交、push、远端校验，全是手工步骤。
历史上出现过：`update.json` 字段漏写、APK 路径拼错导致「点安装没反应」、
`raw.githubusercontent.com` 被重置但 push 其实成功。

**教训**：发版清单必须固定成脚本或 checklist；每次发版做端到端自检
（设备下载远端 APK → 校验 sha256 → 安装）。

## 3. 「验证不缜密」的具体表现

以下都是本项目真实发生过的「假验证」：

1. **只跑 `assembleRelease`，没装到设备**：v1.7.0 冷启动崩溃。
2. **只测正常网络**：v1.9.x 的弱网/截断问题。
3. **只测成功路径**：合流只测首领成功，没测首领失败/取消。
4. **只看 HTTP 状态码**：响应体流中断看不见。
5. **只点 UI，不看日志/落盘取证**：失败被静默吞掉，用户只看到「暂无内容」。
6. **只改字面量，不抓服务端响应**：收藏状态三次改错。
7. **只跑一次冷启动，不测覆盖安装**：签名/迁移/旧数据兼容问题漏掉。
8. **只测浅色主题**：深色描边/对比度回归。
9. **只看编译警告为空**：Kotlin 对未使用 import、死代码、协程误用并不总是报错。
10. **用提交说明「零崩溃」代替可复现的测试记录**：下一个人无法复跑。

## 4. 这次清理做了什么（2026-11）

### 4.1 真实缺陷

- **多词搜索死循环**：阶段 2 只有在返回非空时才推进游标；服务端返回空页（合法情况）
  会导致同一页被无限重拉，直到触发限流。修复为「成功即推进游标；本轮全失败即收口」。
- **解码尺寸漂移**：`ReaderViewModel` 预取宽度写死 2160，改为共享
  `MAX_DECODE_WIDTH_PX` 与 `maxDecodeHeightPx()`，避免预取与展示缓存键尺寸不一致。

### 4.2 去重与收敛

- 新增 `applyStatusAndSort` / `filterByStatus`，分类页与作者页不再各写一份 when。
- 新增 `SERVICE_PAGE_SIZE` / `pageCount` / `pageSlice` / `loadedPageCount`，
  分页条、筛选切片、多词搜索共用一套口径。
- 新增 `comicGridMetrics`，真实网格与骨架屏共用间距。
- 新增 `Source.searchWithRetry`，关注流与搜索页共用重试/取消语义。
- 新增 `fetchPagesInOrder`，章节列表与章节图片共用「并发 + 冷却 + 失败串行补拉」。
- 新增 `isNetworkMetered`，下载调度器与下载页共用判定。
- 删除死代码颜色别名。
- 全仓库全限定名从 454 行降到 ~40 行（剩余主要是 KDoc 链接和字符串内引用）。

### 4.3 取消安全

- `SearchHistory` / `ReaderPrefs` / `ReaderStatus` 的 suspend 路径改用
  `runCatchingCancellable`，不再把协程取消当成普通失败继续写状态。

### 4.4 测试

新增：
- `ComicListFilterTest`：状态筛选 + 四种排序 + 组合顺序。
- `PageMathTest`：总页数、已加载页数、切片边界、页码窗口。
- `PagedFetchTest`：按页序返回、失败补拉、冷却跳过、缺页显式失败。

### 4.5 仍然存在的债

- `ReaderScreen` 1500+ 行、主 Composable 900+ 行，尚未拆分。
- 图片三层拦截器的契约仍靠类注释维系，缺少集成级故障注入测试。
- `data/` 下多个 SharedPreferences+JSON 单例仍有模板重复。
- 仓库历史 APK 较大；发版 APK 仍入库（更新通道需要）。
- UI 字符串全部硬编码中文，未做资源化；这是产品选择，不是本次清理目标。

## 5. 给未来 agent 的检查清单

改动前：

- [ ] 这个逻辑是否已有共享实现？搜索 `AGENTS.md` 第 3.1 节列出的符号。
- [ ] 失败会发生在哪个层次（网络/协议/解析/状态/UI）？
- [ ] 这段代码在协程里吗？取消会发生吗？`runCatching` 会不会吞掉它？
- [ ] 分页/循环的退出条件是否覆盖「空页成功」和「全部失败」？
- [ ] 新增常量是否和现有常量重复？

改动后：

- [ ] `compileReleaseKotlin` + `testReleaseUnitTest` 通过。
- [ ] 新逻辑有能复现原 bug 的测试。
- [ ] UI 冷启动实测；涉及主题/字号/阅读器时覆盖对应矩阵。
- [ ] 网络/下载改动做了故障注入。
- [ ] `python tools/code-health.py --check` 没有让指标变差。
- [ ] 提交说明写清验证方式；如果没测，明确写「未测」。

## 6. 一句话备忘

> **不要用「看起来对」证明对；用能复现的证据证明对。**
> 如果这次修复只能靠手点才能确认，那就把它变成测试，或者至少写清手点步骤。
