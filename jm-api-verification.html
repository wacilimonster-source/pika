2三条核心结论

验证结果推翻了之前方案里的两个前提假设，也确认了一个好消息。

结论 1 · 现有禁漫源代码 100% 不可用，不是"功能缺失"而是"完全不通"。
JmClient 里 6 个端点全部写成 /api/v3/xxx，实测该前缀已废弃，服务端返回 {"code":200,"errorMsg":"Not legal.api"}。同时代码既没有生成 token/tokenparam 签名，也没有解密响应 data，且默认域名 api.jmcomic1.com 已无法访问 API。也就是说，当前 App 切到禁漫源后，任何请求拿到的都是密文或错误，连分类列表都拉不到。
结论 2 · 图片解码这个最大风险项，实测不存在。
之前判断"禁漫图片按 scramble_id 分段打乱，项目未实现解码"是最大工作量风险。本次对 2018~2026 年跨年代 20 个本子逐个请求 /chapter_view_template 提取 scramble_id，20/20 全部为 220980（不分割）。抽取 10 个本子实下载首图与中图，全部 HTTP 200 且为合法 WEBP（960×1342 ~ 1280×1790）。
结论：按现有"直链 + Coil"的方式就能正确显示，不需要写解码算法。建议仍保留 scramble_id 探测作为防御性检查，一旦出现非 220980 值再补算法。
结论 3 · 能力面比预想的好，但有两个参数是死的。
排行榜（日/周/月）、评论、相关推荐、每周必看全部免登录可用，且哔咔有的禁漫基本都有。但：t 时间筛选参数在 /categories/filter 上完全无效（a/t/w/m 返回结果完全一致）；c=3D 和 c=meiman 的分类值映射是错的（分别返回"其他類"和"English Manga"）。分类正确取值应从 /categories 的 slug 字段动态获取。

4现有代码的 5 个致命缺陷

全部位于 network/JmClient.kt，按"修复后才能跑通"的顺序排列。

1 DEFAULT_BASE api.jmcomic1.com 已不作 API 域用。实测 /api/v3/categories 返回 404 重定向脚本，根路径 302。
可用域名：www.cdngwc.cc / www.cdnhjk.net / www.cdngwc.net / www.cdngwc.club		 换默认域名 + 多域名轮换
2 所有 6 个端点路径 /api/v3/ 前缀已废弃。实测 /api/v3/categories → {"code":200,"errorMsg":"Not legal.api"}。

签名：token=md5(ts+"185Hcomic3PAPP7R")，tokenparam="{ts},2.1.5"		 每次请求动态生成

5修复方案骨架

核心是给 JmClient 加签名与解密，改动集中在 execute() 一个方法内。以下为已验证可跑通的实现。

5.1 签名与解密

// network/JmCrypto.kt
object JmCrypto {
    private const val APP_TOKEN_SECRET = "185Hcomic3PAPP7R"
    private const val APP_DATA_SECRET  = "185Hcomic3PAPP7R"
    private const val SCRAMBLE_SECRET   = "18comicAPPContent"  // 仅 /chapter_view_template
    const val APP_VERSION = "2.1.5"

    data class Sign(val ts: Long, val token: String, val tokenparam: String)

    fun sign(secret: String = APP_TOKEN_SECRET): Sign {
        val ts = System.currentTimeMillis() / 1000
        return Sign(ts, md5("$ts$secret"), "$ts,$APP_VERSION")
    }

    // base64 -> AES-256-ECB -> 去 PKCS7 padding
    fun decrypt(data: String, ts: Long, secret: String = APP_DATA_SECRET): String {
        val raw = Base64.decode(data, Base64.DEFAULT)
        val key = md5("$ts$secret").toByteArray()   // 32 hex chars -> AES-256
        val c = Cipher.getInstance("AES/ECB/NoPadding")
        c.init(Cipher.DECRYPT_MODE, SecretKeySpec(key, "AES"))
        val out = c.doFinal(raw)
        val pad = out[out.lastIndex].toInt()
        return String(out, 0, out.size - pad, Charsets.UTF_8)
    }

    private fun md5(s: String) = MessageDigest.getInstance("MD5")
        .digest(s.toByteArray()).joinToString("") { "%02x".format(it) }
}

5.2 改造 execute()

// JmClient.kt：请求带签名，响应自动解密
private suspend fun execute(
    relative: String,
    body: String? = null,
    secret: String = JmCrypto.APP_TOKEN_SECRET,
): String = withContext(Dispatchers.IO) {
    val sign = JmCrypto.sign(secret)
    val builder = Request.Builder()
        .url(baseUrl.trimEnd('/') + relative)
        .header("token", sign.token)
        .header("tokenparam", sign.tokenparam)
    headers.forEach { (k, v) -> builder.header(k, v) }
    if (body != null) builder.post(body.toRequestBody("application/json".toMediaType()))
    else builder.get()

    client.newCall(builder.build()).execute().use { resp ->
        val text = resp.body?.string().orEmpty()
        if (!resp.isSuccessful) throw JmException("禁漫接口 ${resp.code}: ${text.take(200)}")
        // 统一解密：data 为 String 时是密文，为 Array/Object 时是明文（如 /setting）
        val el = Json.parseToJsonElement(text).jsonObject["data"]
        if (el is JsonPrimitive && el.isString) {
            val plain = JmCrypto.decrypt(el.content, sign.ts, secret)
            text.replace("\"data\":${Json.encodeToString(el.content)}", "\"data\":$plain")
        } else text
    }
}
注意 /setting 的 data 是明文对象（{"version":"1.8.2",...}），不是密文字符串。解密逻辑必须对 JsonPrimitive(isString) 做类型判断，否则会崩。这是实测踩到的坑。
