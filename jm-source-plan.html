禁漫源（JMComic）功能规划方案

目标：让禁漫源在 PiKA 内提供与哔咔源一致的阅读体验，对禁漫独有的能力给出独立实现路径。本文档基于现有代码与禁漫移动端 API 调研产出，不含代码实现。

4核心差异与实现方案

两个源的数据结构差异集中在 6 个点。前 3 个必须处理，否则体验不可用；后 3 个是产品形态差异，决定 UI 如何适配。

D1 · 图片分段打乱（scramble）解码最大差异P0

差异：哔咔的 media.directUrl 是可直接渲染的图。禁漫的图片按 N 段切割后乱序存储，直接按直链加载会得到上下错位的图。还原需要 scramble_id，三种取值：220980（不分割，可直出）、268850、421926（2023-02-08 后的新算法）。

现状风险：当前 JmClient 直接拼 https://{host}/media/{folder}/{name} 交给 Coil，没有解码环节。若所看本子命中分割算法，图片就是乱的。这一项需要真机抽样验证后才能确定影响面。

实现方案：

  • 新增 JmImageDecoder：下载字节流 → 按 scramble_id 选算法 → 10 段重排还原 → 输出 Bitmap
  • scramble_id 从 /chapter_view_template 的 HTML 里正则提取，按 album 维度缓存（同一 album 的 scramble_id 相同）
  • 解码结果写入磁盘缓存（复用 DownloadManager 的缓存目录），Coil 加载本地 file，避免每次重解码
  • 阅读器与离线下载共用同一解码入口，下载时必须存还原后的图，否则离线阅读同样错乱
  • 前置动作：先用 10 个不同年代的本子抽样验证"是否需要解码 / 命中哪种算法"，再决定工作量
D2 · 排序：服务端参数 vs 客户端重排半阻塞P0

差异：哔咔 4 种排序全部由服务端完成。禁漫当前只声明支持 LD / VD，且是"取回一页后客户端重排"——这意味着排序只在当前页内生效，翻页后顺序会乱，是个隐性 bug。

实现方案：切换到 /categories/filter，把排序交给服务端：

// ComicSort → 禁漫 o 参数
DD（新到旧）  -> "mr"          // 最新
LD（最多喜欢）-> "tf"          // 最多喜欢
VD（最多观看）-> "mv"          // 最多观看
DA（旧到新）  -> "mr" + 客户端反转 // 禁漫无升序参数
// 时间范围（禁漫特有，可作为筛选器）
t=今日 / w=本周 / m=本月 / a=全部
// 排行榜
H24 -> "mv_t"   D7 -> "mv_w"   D30 -> "mv_m"

切换后 supportedSorts 可放开为全部 4 种，与哔咔一致；时间范围作为额外筛选维度，仅禁漫源显示。

D3 · 收藏：单一列表 vs 收藏夹可对齐P0

差异：禁漫网页端有"收藏文件夹"（folder_id）概念，但 移动端 API 明确不支持 folder_id 参数（社区 SDK 源码注释：移动端没有提供 folder_id 参数）。

实现方案：移动端只使用默认收藏夹，favourite() 与 favourites() 的语义与哔咔完全对齐，UI 无需改动、不引入文件夹层级。收藏夹管理放到 P2 视需求再评估（需要网页端实现，成本高收益低，建议不做）。

D4 · 分类：固定枚举 vs 动态列表需 UI 适配P0

差异：哔咔的分类是接口下发、带封面图、可在"分类管理"里排序与隐藏。禁漫的分类是固定的 10 个枚举值，无封面、不可排序。

实现方案：分类页按"有无封面"自适应——禁漫源走文字 chip 网格布局（单列 chip 墙），哔咔源保持封面网格。分类管理（排序/隐藏）功能对禁漫源隐藏。禁漫固定分类：全部 / 同人 / 单本 / 短篇 / 其他 / 韩漫 / 美漫 / cosplay / 3D / 英文站 / 禁漫漢化組。

D5 · 搜索维度：关键词 vs 多维度可对齐并超出P0

差异：哔咔搜索支持分类/标签/作者/汉化组/上传者/完结状态组合筛选。禁漫搜索走 main_tag 维度切换：0 综合 / 1 作品 / 2 作者 / 3 标签 / 4 角色。

实现方案：把禁漫的 main_tag 映射为搜索页顶部的维度切换 Tab（综合/作品/作者/标签/角色），这比哔咔的"关键词统一搜"其实更符合禁漫用户习惯。详情页点作者 → 走 main_tag=2 的作者搜索；点标签 → main_tag=3。筛选面板里的"汉化组/上传者/完结状态"对禁漫隐藏（源不支持）。

D6 · 账号体系与社区能力待实测P2

差异：哔咔有等级/经验/称号/签名体系，禁漫没有；禁漫有每日签到与浏览历史，哔咔没有。评论能力两者都有但字段不同（禁漫评论含剧透标记）。

实现方案：

  • 统一模型 ComicUser 的 level/exp/title 对禁漫留 0，UI 按"值是否有效"决定是否显示等级模块
  • 禁漫独有：签到卡片、浏览历史入口（作为服务端续读的补充数据源）
  • 评论区：确认端点后接入；不支持则走能力声明隐藏。禁漫的"剧透"标记可映射为评论的折叠态
  • 注册/忘记密码/改资料：确认端点后接入，不支持则隐藏入口，登录页自动退化为纯登录

5架构改造：用能力声明替代异常降级

当前"不支持就抛异常"的契约只能靠调用方 try-catch，而 5 个页面漏了 catch。改为显式声明能力，UI 按能力决定入口显隐，一处改动全局生效。

现状（隐式）
// Source 接口
suspend fun favourites(page: Int) =
  throw UnsupportedOperationException(...)

// 调用方：只有详情页写了 catch
try { source.favourites(page) }
catch (e: UnsupportedOperationException) { ... }
// 收藏页 / 排行榜 / 我的页：无 catch → 崩溃
改造后（显式）
enum class SourceCapability {
  FAVOURITE, RANK, RANDOM, RECOMMENDATION,
  COMMENT, MY_COMMENTS, PROFILE, PROFILE_EDIT,
  REGISTER, FORGOT_PASSWORD, HOT_WORDS, TAGS,
  TIME_FILTER, SEARCH_DIMENSION, DAILY_CHECKIN
}

interface Source {
  val capabilities: Set<SourceCapability>
}

// UI：入口按能力显隐，不需要 catch
if (SourceManager.current()
      .capabilities.contains(FAVOURITE)) { ... }
收益：① 一次性修掉禁漫源下 5 个页面的崩溃隐患；② 新接入数据源时只需声明能力清单，UI 自动适配；③ 可以据此生成"当前源支持哪些功能"的设置页说明；④ 保留原有的 UnsupportedOperationException 作为兜底（能力声明与实现不同步时仍不崩）。

接口拆分：当独有功能超过 5 个时

能力声明解决的是"调用不崩"，但没解决接口膨胀——Source 现有 27 个方法，禁漫独有功能还会继续往上加。届时按能力域拆开，让"是否支持"从运行期判断变成编译期可见。

拆分方案
// 核心：任何源都必须实现
interface SourceCore {
  suspend fun browse(...): PageResult<ComicSummary>
  suspend fun search(...)
  suspend fun comicDetail(id: String): ComicDetail
  suspend fun chapters(id: String): List<ComicChapter>
  suspend fun chapterPages(...)
}

// 社区：可选实现
interface SourceSocial {
  suspend fun favourites(page: Int)
  suspend fun comments(...)
  suspend fun profile(): ComicUser
}

// 禁漫独有：只有部分源实现
interface SourceExtras {
  suspend fun dailyCheckIn()
  suspend fun history(page: Int)
  suspend fun weeklyPicks()
}

// 调用方：类型判断，编译期可见
(source as? SourceExtras)?.dailyCheckIn()
收益与取舍
  • 编译期挡住误用：as? SourceExtras 拿不到就是不支持，不需要 try-catch，也不会漏判
  • 接口不再膨胀：新能力加进对应子接口，SourceCore 保持稳定，已有实现不用跟着改签名
  • 能力清单可自动化：capabilities 由"实现了哪些子接口"反推，不用手工维护枚举，避免声明与实现不同步
  • 代价：调用点从 source.favourites() 变为 (source as? SourceSocial)?.favourites()，涉及全部社区能力调用点改造
时机建议：不要现在拆。当前 P0 的首要矛盾是"5 个页面会崩"，能力声明机制已经能解决。等独有功能落地超过 5 个、或 Source 方法数超过 35 个时再拆，避免过早抽象拖慢止血进度。

6禁漫独有功能

禁漫的能力面比哔咔宽，而且宽在一个哔咔没有的维度：它是带社区运营的内容站（签到、历史、博客、小说、徽章），哔咔只是一座漫画库。下面 9 项是"哔咔没有、禁漫有"的候选，按用户价值与实现成本排布。

为什么签到排第一：它是全部候选项里唯一能形成日活钩子的功能——用户每天打开 App 有实际收益。实现只需 2 个端点加一张卡片，成本低于任何一项对齐工作，但产品收益高于多数对齐项。

收藏夹分组的结构性优势：哔咔的收藏是一个扁平列表，禁漫支持多文件夹加收藏标签，这是结构上强于哔咔的地方，值得做成差异化亮点。但移动端 v3 是否开放了 folder_id 需要实测——网页端确定支持，移动端存疑。

功能端点实现方式成本
小说频道 novel 子系统：列表 / 搜索 / 章节正文 / 收藏 / 评论 需新增内容类型、文本阅读器（与现有图片阅读器完全不同）、新路由与数据模型 5~7 天
官方博客 + 徽章称号 /blogs / /blog；user 模块 badges 博客做首页公告条或「发现」页；徽章在 profile 卡片展示 1~2 天
小说频道是最大的差异化点，也是最大的坑。禁漫有完整的小说子系统，这是唯一一项哔咔根本无法对齐的能力。但它要求一整套文本阅读器（排版、字号、夜间模式、滚动位置记忆），与现有图片阅读器几乎没有可复用部分。除非计划把 PiKA 做成内容站，否则建议放到最后评估。

不建议做

  • JCoins 购买（/coin_buy_comics）：涉及支付流程与合规风险，与阅读器定位无关
  • 移动端注册：官方未开放，登录页保持隐藏注册入口即可

两项必须前置的前提

1 · 端点前缀必须实测。本节列出的路径多来自社区客户端源码整理，其中相当部分是网页端路径（/daily、/watch_list、/week、/favorite）。而项目 JmClient 走的是移动端 /api/v3/ 前缀，两者不一定一一对应。建议抓一次官方 App 的包，或持 token 逐个试探，约半小时即可确认可用清单。在此之前不要写业务代码。
2 · 能力声明必须先落地。每加一个独有功能，就多一个"哔咔源不支持"的调用点。当前 UI 层只有详情页做了 try-catch，收藏页、首页排行榜、「我的」页全是裸调用——直接加签到卡片会导致切回哔咔源时崩溃。第 5 节的 SourceCapability 必须先于本节任何功能落地。

7实施路线

按"先止血、再对齐、后差异化"三阶段推进。P0 完成后禁漫源即可作为可用源日常使用。

P0 · 止血与基础对齐建议优先约 2~3 天
目标：禁漫源下不再崩溃，核心浏览链路（分类 / 排行 / 搜索 / 收藏 / 阅读）完整可用。
  • 引入 SourceCapability 机制，5 个漏 catch 的页面接入能力判断
  • 抽样验证图片 scramble 影响面；确认后实现 JmImageDecoder + 磁盘缓存（含下载模块）
  • browse 切换 /categories/filter，支持 4 种排序 + 时间范围
  • 接入 /favorite GET / POST，打通收藏与收藏列表
  • 排行榜：用 o=mv_t / mv_w / mv_m 实现日 / 周 / 月榜
  • 搜索接入 main_tag 维度切换与排序参数
  • 分类页适配无封面布局（chip 墙）
P1 · 体验对齐次之约 2~3 天
目标：把社区与发现类能力补齐到接近哔咔的水平。
  • 抓包确认并接入评论端点（列表 / 发送 / 回复 / 子评论 / 我的评论）；不可用则按能力隐藏
  • 个人资料接入，"我的"页显示用户信息（等级相关字段留空并隐藏）
  • 随机推荐与相关推荐：优先找官方端点，无则用分类随机页 / 同作者同标签兜底
  • 热搜词与标签词表：官方端点优先，否则本地静态表 + 标签聚合
  • 域名自动分流：/setting + 延迟探测，替代设置页手填域名
  • JmClient 统一错误处理与重试（镜像域名切换）
P2 · 禁漫差异化能力可选视需求
目标：把禁漫有而哔咔没有的能力做成产品亮点，而不是简单对齐。候选清单、端点与价值排序见 第 6 节。
  • 每日签到卡片（禁漫独有，用户有实际收益）
  • 浏览历史：作为服务端续读来源，与本地进度互补 / 冲突合并策略
  • 账号管理：注册、找回密码、改资料、换头像
  • 小说 / 画册子系统（禁漫独有的内容形态，需新增内容类型与阅读器适配，成本高，建议单独立项评估）

9风险与待验证清单

按"是否阻塞 P0"排序。带"需实测"的项目必须在动手前验证，否则可能做无用功。

风险项影响验证方式应对
图片 scramble 解码未实现阻塞抽样 10 本不同年代本子，比对直链图与解码图确认命中算法后实现解码器 + 缓存；若全部为 220980（不分割）则本项降级为 P2
规划端点路径前缀不确定阻塞抓包官方 App 一次完整会话不照抄社区文档路径；先抓包再编码

需登录端点在未登录时的行为中未登录调用收藏 / 评论统一 401 处理，复用 SourceManager 的 unauthorizedTick 跳登录
评论能力可能移动端不支持中抓包确认按能力声明隐藏评论区，不影响主链路
